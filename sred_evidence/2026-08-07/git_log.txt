    fix: single Ollama daemon lifecycle - no more duplicates or connection gaps
    
    Two defects produced duplicate/orphaned ollama.exe processes and
    intermittent 'Failed to fetch':
    
    1) start_inference_server checked 'ollama list' with .output().is_ok(),
       but is_ok() is true for ANY exit code - including exit != 0 when no
       daemon is reachable. So VERA always concluded a daemon was running,
       returned early without setting the guard, and NEVER spawned or ever
       killed anything (guard stayed None). The real reachability check is
       exit status .success() (0 means the daemon answered).
    
    2) list_installed_models fallback spawned a bare 'ollama serve' with no
       OLLAMA_HOST/OLLAMA_ORIGINS and no stored child handle whenever the
       daemon was unreachable. That orphan outlived the app (no kill on
       exit, no wait) and duplicated the managed daemon, creating windows
       with nothing listening on 11434 mid-handoff.
    
    Fixes:
    - start_inference_server: reuse VERA-managed child if any; reuse
      external daemon only if 'ollama list' exits 0; otherwise spawn with
      the CORS-correct origins and take ownership.
    - list_installed_models: never self-heal; return empty and let
      start_inference_server (the single spawn site) own the lifecycle.
    - stop_inference_server / factory_reset / exit_app: kill + wait() so
      the port is fully released before any respawn.
    - vera-server binary: same exit-code fix, and kills its daemon on
      shutdown instead of leaking it.
    - New ~/.lexsort/logs/ollama-lifecycle.log: every spawn/reuse/kill
      decision timestamped with PID and reason.
    
    Bump to v1.1.11 for clean-machine verification.

    fix: remove invalid tauri:// origin that crashes Ollama (CORS root cause)
    
    OLLAMA_ORIGINS contained 'tauri://localhost', which gin-contrib/cors
    v1.7.2 (bundled in Ollama v0.9.6) rejects at startup - Validate() panics
    with 'bad origin' because only http(s)/extension schemes are allowed. So
    VERA-spawned Ollama crashed immediately after spawn.
    
    When Ollama was instead already running externally (ollama list succeeds),
    start_inference_server returned early and left the default origins
    (tauri://* but NOT http://tauri.localhost) - the Windows WebView2 origin.
    Preflight OPTIONS returned 403 which the webview collapses into
    'Failed to fetch'. Confirmed experimentally: sanitized origin list allows
    http://tauri.localhost preflight (204 + correct Allow-Origin header).
    
    Fix: drop the tauri:// scheme from OLLAMA_ORIGINS at both spawn sites
    (lib.rs start_inference_server, server.rs start_ollama), keeping
    http://tauri.localhost + http defaults. Also log window.location.origin
    in chat-debug.log on each send for field verification.
    
    Bump to v1.1.10 (CORS release for clean-machine Windows re-test).

    ci: fix race where parallel builds create the same release and lose assets
    
    Windows v1.1.8 build created the release but uploaded zero installers —
    only auto-generated source archives were attached. Root cause: tag push
    (3x mac/linux matrix jobs) + manual Windows dispatch all raced to call
    createRelease on the same brand-new tag. tauri-action#1270: after
    createRelease, GitHub's releases API can return 404 on the upload path,
    and with retryAttempts defaulting to 0 the step fails and assets are lost.
    
    - New prepare-release job creates (or finds) the release once on ubuntu
      before any build starts and passes release_id to every platform job
    - Platform jobs upload via releaseId instead of tagName; uploads retried
      retryAttempts: 3
    - concurrency group keyed on the tag ref (push) or tag_name input
      (dispatch) serializes runs targeting the same release; a Windows build
      in flight is never cancelled (cancel-in-progress: false)
